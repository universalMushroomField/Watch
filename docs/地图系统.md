# 地图系统

> 相关：`docs/战斗系统.md`、`docs/主题与叙事.md`（崩解度的叙事含义）、`docs/资源需求.md`

地图是一张铺在三维地形上的**六边形蜂巢顶点网络**：中间是 `columns × rows` 个六边形格子组成的完整蜂巢，最左端一列顶点是起点，最右端一列顶点是本幕 Boss。地图不画实体格子，只画格子之间的边和顶点：每个顶点是一颗小球（贴地的附着点 + 略高一点的交互点），每条边是一条贴着地形走的折线，整张图看起来像架在地形上的一张青色线网。

线网直接采样真实三角网格：`MapSurfaceSampler` 按 1 米分箱缓存地形三角面，用向下射线取每个点的最高地表高度；线段在 XZ 平面上与三角形边相交的位置切分，台阶处分别取两侧高度并竖直相连，因此线不会穿进地形里，也不会在半空飞过台阶。

移动规则沿用原来的设计：每一步可以选择**任意已探索节点的未探索邻居**，不必从当前所在节点出发；已经探索过的节点不能再次进入。因此玩家可以回到早先的分支点改走另一条路，但不会重复经过同一个节点。

## 节点类型

| 类型 | 说明 |
| --- | --- |
| 起点 | 每幕开始的位置，已自动访问，位于最左端顶点列 |
| 战斗 | 普通战斗，胜利后获得金币（见 `docs/战斗系统.md`） |
| 精英战斗 | 更难的战斗，金币更多，只会出现在第 2 列及以后 |
| 未知事件 | 随机触发一个事件，按选项结算（见 `docs/事件系统.md`） |
| 宝箱 | 获得金币 |
| 商店 | 购买卡牌或治疗，库存有限（见 `docs/商店系统.md`） |
| 休息点 | 恢复最大生命的一定比例 |
| 关底 Boss | 位于最右端顶点列，进入后可以开启下一幕；每幕一个，见下文「幕与 Boss」 |

## 幕与 Boss

一局共三幕，每幕一张地图，关底各有一个 Boss；三个 Boss 的出场顺序每局随机，不会固定由同一个 Boss 开场。地图本身相对较小，当前默认 `4 × 4` 个格子（`map/res/data/map_config.tres`），实际尺寸还会按地形与相机视野缩小，目标值待定。

当前实现：`MapRun.advance_act()` 可以无限开启下一幕，幕数没有上限，也没有 Boss 内容（`map/templates/node/content/` 只有战斗、商店、事件的占位场景）。

## 崩解度

崩解度 = 本幕已访问的非起点节点数 / 本幕非起点节点总数，每幕开始时重置。起点不参与计算，所以开局是 `0%`（`0 / (节点总数 - 1)`，默认布局下是 `0/53`）；走遍其余节点后达到 `100%`。

移动规则允许从任意已探索节点出发，因此上升量分两种：

- 直接访问新节点：按访问数量正常上升。
- 绕经已访问节点去访问新节点：上升量更高。玩家为了凑路线在旧节点之间折返，会额外推高崩解度。

第二条还没有实现：`travel_to()` 只判断目标是不是某个已探索节点的未探索邻居，既不计算从 `current_id` 到目标的路径，也不统计途经的已访问节点，崩解度只随访问数量线性增长。

目前只提供数值与信号（`MapRun.decay_changed`、`MapRun.act_completed`），尚未绑定任何减益效果，方便后续单独设计。崩解度在叙事上就是族群的极端度，六个极端度阶段见 `docs/主题与叙事.md`；减益曲线的数值需求见 `docs/资源需求.md` 的数值需求。

## 坐标与布局

`HexLayout` 保存中间区域的列数、行数和六边形外接圆半径。中间区域是 `columns × rows` 的完整蜂巢，起点单独占最左一列顶点，Boss 占最右一列顶点，总列数是 `columns + 2`。**地图节点是六边形的顶点，不是六边形的中心**，相邻的格子共用顶点，因此节点总数远大于格子数。

采用**尖顶（pointy-top）**六边形。第 `c` 列、第 `r` 行的格子中心在整数格坐标上是：

```text
center = (2 * c + (r & 1), 3 * r)
角点   = center + (±1, ±1) / (0, ±2)
```

每个格子的 6 个角点合并进同一张顶点表，节点保存的就是这个整数格坐标 `vertex`。世界坐标换算时按半格缩放，再绕 Y 轴旋转到与相机屏幕对齐：

```text
局部 x = vertex.x * sqrt(3) * R / 2
局部 z = vertex.y * R / 2
世界   = rotate(局部, board_angle) + board_offset
```

其中 `board_angle = atan2(camera.basis.x.z, camera.basis.x.x)`，保证列方向与相机的屏幕右方向一致（起点在左、Boss 在右）；`board_offset` 把整张顶点网络的包围盒居中到可用矩形里。`R` 是六边形外接圆半径，因此整数格的一个水平单位对应世界距离 `sqrt(3)/2 * R`，一个竖直单位对应 `R/2`。

顶点之间只有蜂巢边：相邻顶点在格坐标上相差 `(±1, ±1)` 或 `(0, ±2)`（即 `3*dx² + dy² == 4`），换算到世界坐标后每条边长都等于 `R`，每个顶点的度数最多为 3。

生成器不会连上所有蜂巢边，而是先随机洗牌所有边、用并查集建立**生成树**保证全图连通，再以 `0.28` 的概率补回剩余边形成可选路线。因此图上既有死路（度 1），也有分叉（度 3）。4×4 上限时是 54 个顶点、至少 53 条边（补边后约 57 条），度数为 1/2/3 的顶点分别是 12/24/18 个；当前实机拟合出的 2×2 是 23 个顶点，补边数随种子变化（种子 1 是 24 条边，度数 2/17/4）。起点在最左端顶点列中随机取一个，Boss 在最右端顶点列中随机取一个，两者不一定在同一行。

### 自适应尺寸

棋盘尺寸不写死。拟合由 `HexLayout.fit(rect, config)` 完成（`map/scripts/hex_layout.gd`），`MapHexLayer.make_layout()` 只负责采样地形和相机、求出可用矩形（世界 XZ）再调用它：

1. 取地形 mesh 的 AABB，向内收缩 `board_margin`。
2. 取正交相机可见的地面范围（由 `camera.size`、视口宽高比和俯角换算，俯角取 `camera` 前向的 Y 分量）。
3. 两者求交。

`MapConfig.max_columns` / `max_rows` / `hex_radius` 是**上限**，不是目标值。按上限半径估算列/行数，并分别限制在上限以内：

```text
columns = clamp(floor(rect.x / (sqrt(3) * R) - 2.5), 2, max_columns)
rows    = clamp(floor((rect.y / R - 0.5) / 1.5), 2, max_rows)
```

再用实际需要的跨度反算半径，保证棋盘完整落在可用矩形里，且不超过目标半径：

```text
R = min(rect.x / (sqrt(3) * (columns + 2.5)),
		rect.y / (1.5 * rows + 0.5),
		hex_radius)
```

半径那一行正是 `get_world_width()` / `get_world_depth()` 的跨度公式反过来解，所以拟合结果必然满足 `width <= rect.x` 且 `depth <= rect.y`。矩形越小，列/行越少；矩形足够大时才会用满 `max_columns` × `max_rows`。

实测（Godot 4.7.2 headless）可用矩形 `[P: (-39.40, -20.34), S: (36.14, 50.20)]`，配合 `map/res/data/map_config.tres` 的 2×2 上限，拟合结果是 **2×2、半径 4.2、23 个顶点**；4×4 需要 47.29 × 27.30 米的矩形，这块地形装不下。

**没有回退布局。** `MapRun` 与 `MapGenerator` 都必须显式传入拟合后的 `HexLayout`，`RunState.create_map(null)` 会 `push_error` 并返回 `null`，`MapGenerator.generate()` 用 `assert` 拦截空布局。这样越界的棋盘不可能被静默渲染出来。

## 地表高度

`MapSurfaceSampler` 只做一件事：回答“世界 XZ 处最高的地表有多高”，并提供贴地折线。

1. **烘焙**：遍历 `terrain.mesh.get_faces()`，把每个三角面乘上 `terrain.global_transform`；只保留法线朝上的面（`(c-a).cross(b-a).y > 0`）。
2. **分箱**：每个三角面登记到它 XZ 包围盒覆盖的所有 `BIN_SIZE = 1.0` 米格子里。
3. **查询** `height_at(point)`：从 `bounds.end.y + 1` 向下发射射线，与候选三角面求交，取最高的交点。
4. **折线** `trace(a, b)`：在 XZ 平面上求线段与所有候选三角形边的交点，按参数排序后切成小段；每段在 25% / 75% 处各取一次高度，两端按半个高差外扩（`y0 - slope` / `y1 + slope`），于是台阶处会出现一段竖直连线，线不会斜穿台阶。

`MapHexLayer` 用两套高度：

- **附着点**：`attachment.global_position.y = height_at(顶点 XZ)`，直接落在地表上。
- **交互点**：`holder` 的初始高度是交互平面 `interaction_plane = 地形 AABB 顶部 + hex_lift`，所有节点共面，方便俯视时点击。

相机放大时，`MapHexLayer._process()` 把 `MapCamera.get_zoom_progress()`（0 = 原始视野，1 = 最大放大）平滑地混进节点高度（`move_toward(..., delta * 5.0)`）：

```text
holder.y = lerp(interaction_plane, attachment.y, zoom_blend)
```

线网同步切换：`AttachmentPaths` 始终贴着地表；`InteractionPaths` 只连两端、高度同样按 `zoom_blend` 混合，完全放大（`zoom_blend >= 0.999`）时隐藏。

## 渲染与交互

- `map/scripts/map_hex_layer.gd`：采样地形、生成顶点小球与贴地折线、放置 `Label3D` 短标签、处理悬停与拾取。所有几何体都是 `unshaded` 的纯色材质，不投影（`SHADOW_CASTING_SETTING_OFF`）。
- 顶点视觉：`Attachment` 球半径 `0.09`、高 `0.18`，青色 `(0.30, 0.74, 0.81)`；`holder` 下的交互球半径 `0.14`、高 `0.28`，暖黄色 `(1.00, 0.78, 0.40)`。
- 折线：`_surface.trace()` 的结果以 `PRIMITIVE_LINES` 拼成 `ArrayMesh`。`AttachmentPaths` 每条边抬 `PATH_LIFT = 0.035` 米，颜色 `(0.28, 0.66, 0.75)`；`InteractionPaths` 颜色 `(1.00, 0.78, 0.40)`。
- 标签：`Label3D` 始终朝向相机（`BILLBOARD_ENABLED`）、`no_depth_test`、字号 `56`、`pixel_size 0.02`、黑色描边 `14`，位置在交互点上方 `0.62` 米，文字是单字短标签（起/战/精/事/宝/商/息/Boss）。
- 颜色规则（`refresh()`）：当前节点白色并放大 `1.22` 倍；悬停节点 `(1.00, 0.95, 0.72)`；可达节点按类型色提亮 `0.55`；不可达节点提亮 `0.05`；已访问且不是当前节点的变灰 `(0.62, 0.65, 0.70)`。类型色表见 `TYPE_COLORS`。
- `MapHexLayer.node_at_screen()`：把每个节点的交互点与标签位置投影到屏幕，命中半径由“交互点 + 相机右方向 × `hex_radius`”的投影距离乘以 `0.35` 得到，并夹在 `12 ~ 34` 像素之间；取最近命中。因为节点是离散小球，不再做六边形点内测试，也不再发射世界射线。
- `ui/gui_map/map_board_input.gd`：盖在 `SubViewportContainer` 上的透明 `Control`。它把本地坐标换算成 `SubViewport` 像素（按容器尺寸与视口尺寸的比例），再做悬停与点击；右键拖动环绕、滚轮放大、滚轮缩小复位。鼠标事件由这一层处理，三维视口保持 `handle_input_locally = false`。
- `map/scripts/map_camera.gd`：正交相机。`orbit_drag()` 绕父节点原点旋转（`orbit_speed = 0.005`），`zoom_at()` 以光标下的世界点为锚点把 `size` 乘以 `zoom_factor = 0.8`，并反算 `h_offset` / `v_offset` 让锚点留在原处；最小缩放为初始视野的 `minimum_zoom_ratio = 0.25`，`reset_zoom()` 复位。
- 白色底模在视口中央完整显示，接近屏幕四边时按流动噪声镂空。主材质的 `edge_width` 控制边带宽度，`block_size` 控制屏幕像素块尺寸，`flow_speed` 控制流速。
- 主材质的 `breakup = 1` 让同一屏幕方格共用一个噪声样本，整格崩解。随后 `Next Pass` 的 `pixel_size` 对底模颜色做最近邻采样，默认 4 像素，设为 1 可单独关闭后处理。
- 粒子雾使用各自的 UV 划分像素格。`ParticleFog` 材质的 `pixels_per_particle` 控制每个粒子横纵方向的格数，数值越小，颗粒边缘越粗。
- `map/shaders/legacy/hex_tube.gdshader` 与 `map/shaders/legacy/terrain_route_blur.gdshader` 是“白色圆管线框 + 路线旁模糊”那一版的遗留资源，当前没有任何场景或脚本引用它们，保留仅为历史参考。

## 单局接入

`run/templates/run.tscn` 是一局游戏的根场景：

```text
Run (Node2D, RunState)
└─ UI (CanvasLayer)
   └─ MapView (ui/gui_map/map_view.tscn)
```

`map_view.tscn` 内部：

```text
MapView (Control)
├─ SubViewportContainer
│  └─ SubViewport (1152×648, render_target_update_mode = Always)
│     └─ MapLayer0 (map/templates/map_layer_0.tscn)
│        ├─ Camera3D (MapCamera, 正交, size 64.161)
│        ├─ MeshInstance3D (地形, camera_edge_breakup 材质)
│        ├─ DirectionalLight3D
│        └─ WorldEnvironment
├─ Margin/VBox: ActLabel / HealthLabel / GoldLabel / DeckLabel / DecayLabel
│               DecayBar / BoardInput / StatusLabel
└─ Overlay: 节点面板（标题、正文、选项按钮）
```

- `RunState` 从 `SeedGenerator.run_seed` 取本局种子，创建 `MapRun` 和 `RunPlayerState`，并把同一个 `MapRun` 交给地图视图。
- 地图视图只负责显示和交互；单局场景向它注入 `RunState`，找不到时（单独运行 `map_view.tscn`）会自己创建一份，方便调试。
- `ui/start_menu/start_menu.tscn` 的「开始游戏」已经指向 `run.tscn`。

### 底模的体素崩解

打开 `map/templates/map_layer_0.tscn`，选中 `MeshInstance3D`。在 Inspector 的 **Voxel Erosion** 中调整参数即可预览。编辑器使用 `preview_seed`，运行时按全局单局种子生成。地图上的节点与附着路径采样生成后的地表。

| 参数 | 作用 |
| --- | --- |
| `voxel_size` | 碎块的基本边长。较小的值保留更多地表细节，同时增加几何量。 |
| `intact_depth` | 每列自地表向下保留的完整厚度比例。山峰和低地分别计算。 |
| `erosion_strength` | 下部岩层的侵蚀强度，设为 0 可预览实心几何。 |
| `cluster_size` | 缺口的空间尺度。调大时，相邻的空洞和残岩会连成较大的区域。 |

地图场景将几何侵蚀强度设为 0，保留实体地表及底面。白模以双面材质绘制，并保留背光面的基础亮度。

## 调整生成结果

在 `map/res/data/map_config.tres` 中修改：

- `max_columns` / `max_rows`：中间蜂巢的**最大**列数与行数，当前 2 / 2；实际值由 `HexLayout.fit()` 按地形和相机视野向下缩，不是目标值。设计目标是每张图相对较小，具体上限待定。
- `hex_radius`：六边形半径的目标值，默认 4.2；棋盘放不下时会自动缩小。
- `hex_lift`：交互平面高于地形包围盒顶部的距离，默认 0.25。
- `board_margin`：棋盘与地形边缘保留的空白，默认 0.5。
- `elite_count` / `shop_count` / `rest_count` / `treasure_count`：各类节点数量，默认 2 / 1 / 1 / 1。
- `event_ratio`：剩余节点中事件的比例，默认 0.5，其余为战斗。

表现与手感参数分布在脚本顶部或导出变量里：

- `map/scripts/map_hex_layer.gd`：`PATH_LIFT`（折线离地距离，0.035）、`TYPE_COLORS`（类型色）、顶点球半径/高（0.09 / 0.18）、交互球（0.14 / 0.28）、标签字号/像素尺寸/描边（56 / 0.02 / 14）、拾取半径系数（0.35，夹在 12~34 像素）。
- `map/scripts/map_surface_sampler.gd`：`BIN_SIZE`（分箱尺寸，1.0 米）。数值越小拾取越准、烘焙越慢。
- `map/scripts/map_camera.gd`：`orbit_speed`、`zoom_factor`、`minimum_zoom_ratio`。
- `map/scripts/map_generator.gd`：`CORNERS`（格子角点）、生成树之外补边的概率（`0.28`）、精英只放在第 2 列及以后（`node.column >= 2`）。

生成器保证全图连通；起点和 Boss 各自在最外侧顶点列里随机取一个，其余地点按类型配额随机分配。

## 调试与测试

地图视图可以单独运行 `map/templates/map_view.tscn`；完整单局入口是 `run/templates/run.tscn`。战斗、商店、事件等节点目前只显示占位内容（`map/templates/node/content/*.tscn`），不结算任何奖励，金币也没有产出途径。

```bash

godot --headless --path . -s res://map/tests/voxel_terrain_test.gd
godot --headless --path . -s res://map/tests/map_view_smoke_test.gd
godot --headless --path . -s res://run/tests/run_smoke_test.gd
```

`map_smoke_test.gd` 跑 200 个种子 × 两组布局：**实机尺寸**用 `map_view` 实测的可用矩形（`36.14 × 50.20`）和真实的 `map_config.tres` 走 `HexLayout.fit()`，即 2×2 / 23 个顶点——拓扑、崩解度分母都和游戏里那套一致，并断言节点数与实机相符；**压力尺寸**用 `MapConfig` 默认上限 4×4 / 54 个顶点，只验证生成器在更大图上的不变量。两组都检查顶点唯一、边合法（`3*dx² + dy² == 4`）、度数不超过 3、全图连通、崩解度计算和换幕；另外扫一遍 8~80 米的不同矩形，断言拟合结果一律不越界，且在宽裕矩形下正好用满配置上限。`map_view_smoke_test.gd` 检查附着点落在地表、交互点初始共面、两组路径覆盖每条边、旋转/缩放后世界 XZ 不变、放大时节点高度向地表过渡、拾取仍然对齐，并实际走到 Boss，同时断言实机棋盘落在 `_available_rect()` 内且不超过配置上限；`run_smoke_test.gd` 检查单局根节点与地图视图共用同一份状态。

实机布局每次跑测试都会打印一行，可直接与运行入口对照：

```text
  实机布局 2×2 R=4.200 span=32.736×14.700 nodes=23 可用矩形=36.140×50.200
```

`map/tests/map_capture.gd` 渲染 `map_view.tscn` 到 `map/tests/layout_preview.png`；`run/tests/run_capture.gd` 渲染完整单局入口到 `run/tests/run_preview.png`，用于目检布局。两张图都在 `.gitignore` 里，只作为本地目检产物；改完表现后重新跑一遍即可。
